TERMINAL JUMP — OOP 네 가지 특징

1. 전체 코드 구조
GameManager.java: 입력, 게임 진행, 발판 생성, 화면 그리기
Player.java: 플레이어 위치, 이동, 점프, 착지
Platform.java: 모든 발판의 공통 추상 부모
NormalPlatform.java: 일반 발판
BreakablePlatform.java: 첫 착지 0.35초 후 사라지는 발판
TimedPlatform.java: 첫 착지 0.8초 후 사라지는 발판
FinishPlatform.java: 도착하면 게임을 완료하는 발판

게임용 클래스는 7개이며 파일도 각각 나눴다.
src/test/java/game/OopBehaviorCheck.java는 별도의 검증용 클래스이다.

2. 캡슐화 — 상태를 보호하고 메서드로 조작한다
Platform의 위치, 너비, active, disappearAt은 private이다.
Player의 위치, 수직 속도, 입력 상태, 착지 상태도 private이다.
감독은 player.x를 직접 수정하지 않는다.
player.setLeft(), setRight(), jump(), spawnOn(), land()를 사용한다.
조회는 getX(), getY(), isActive() 같은 메서드를 사용한다.
발판 자식은 disappearAt을 직접 고치지 못한다.
부모의 protected final scheduleDisappear()를 사용하므로,
재착지해도 최초 소멸 시각을 연장하지 않는 규칙이 유지된다.
모든 필드에 setter를 만들지 않고 필요한 동작만 공개했다.

3. 상속 — 공통 기능을 부모에서 물려받는다
NormalPlatform, BreakablePlatform, TimedPlatform, FinishPlatform은
모두 extends Platform으로 선언했다.
부모의 위치 정보, 조회 메서드, 소멸 처리 update()를 물려받는다.
super(text, x, y, width)는 부모 생성자를 호출해 공통 정보를 설정한다.
서로 관계없는 Player와 GameManager를 상속시키지 않았다.

4. 추상화 — 공통 규격과 구체적인 구현을 구분한다
Platform은 abstract class여서 new Platform(...)으로 직접 만들 수 없다.
public abstract void touched(double elapsed);
public abstract String getColor();
두 추상 메서드는 모든 발판이 제공해야 하는 기능을 정의한다.
각 자식 클래스가 구체적인 착지 반응과 색상을 구현한다.
감독은 내부 소멸 시각 계산을 알 필요 없이 touched()만 호출한다.

5. 다형성 — 부모 타입으로 같은 명령을 내리되 실제 객체마다 다르게 반응한다
GameManager의 List<Platform>에는 여러 종류의 자식 발판이 함께 들어간다.
착지한 발판도 Platform landing 변수로 다룬다.
landing.touched(elapsed)를 호출하면 실제 객체의 재정의된 메서드가 실행된다.
- NormalPlatform: 유지
- BreakablePlatform: 0.35초 뒤 소멸 예약
- TimedPlatform: 0.8초 뒤 소멸 예약
- FinishPlatform: 유지, isFinish()는 true
화면 색상도 p.getColor()로 얻는다.
@Override는 부모 메서드를 재정의한다는 표시다.
단순히 메서드 이름이 같은 것이 아니라, 부모 타입으로 자식 객체를 참조하고
호출할 때 실제 객체의 구현을 선택한다는 점이 핵심이다.

6. 기존 코드와 달라진 점
기존: 하나의 Platform에서 Type enum과 if로 종류별 반응을 구분.
수정: 발판 종류별 자식 클래스로 동작을 분리하고 공통 부모 타입으로 관리.
발판을 무작위 생성할 때 어떤 클래스를 생성할지 고르는 if는 남아 있다.
이 if는 생성할 객체를 선택하는 부분이며, 착지 반응은 다형성으로 처리한다.
소멸 시간, 색상, 안전 경로, 조작키, 점프 수치 등 기존 규칙은 유지했다.
Player.update()가 프레임 시작 시 착지 상태를 초기화하도록 옮겼다.
TeaVM requestFrame의 JSBody에 누락되어 있던 callback 파라미터 선언도 추가했다.
기존 HTML/CSS/이미지와 Gradle 설정은 유지했다.

7. 발표할 때 사용할 설명
“발판의 공통 속성과 기능은 Platform 추상 클래스로 정의했습니다.
일반 발판, 일회용 발판, 시간제한 발판, 도착 발판은 이를 상속합니다.
감독은 발판들을 Platform 타입으로 관리하며, 같은 touched 메서드를 호출해도
실제 발판 종류에 따라 다른 동작을 수행하도록 다형성을 적용했습니다.
플레이어와 발판의 상태는 private으로 보호하고,
공개된 메서드를 통해서만 변경하도록 캡슐화했습니다.”

8. 검증 범위
Java 21의 컴파일러와 실제 TeaVM JSO 0.16.0 API JAR로 전체 자바 소스를 컴파일했다.
OopBehaviorCheck 실행 결과: 15개 검사 통과.
검사: 소멸 시간 경계, 재착지 시 소멸 연장 방지, 일반/도착 발판 유지,
도착 여부, 색상, 플레이어 생성, 상승, 상승 중 착지 금지,
공중 점프 금지, 낙하 후 착지, 소멸 발판 착지 금지, 좌우 경계.
TeaVM 전체 Gradle 빌드와 브라우저 실행은 검증하지 않았다.
제출 전 IntelliJ에서 Gradle 빌드 및 브라우저 조작 확인이 필요하다.
